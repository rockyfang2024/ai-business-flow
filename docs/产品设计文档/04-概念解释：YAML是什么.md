# 04 概念解释：YAML 是什么

> 目标读者：业务人员、产品经理、需求方
> 读完本文，你将理解什么是 YAML、为什么流程要用 4 个文件来描述、以及每个文件里装的是什么。

---

## YAML 是什么？

**YAML** 是一种"用文字描述结构化数据"的格式，读作"亚姆尔"（类似"骆驼"的英文写法）。

它的设计初衷是：**让人类能轻松读懂，同时机器也能轻松解析**。

### YAML 长什么样？

举一个最简单的例子：

```yaml
流程名称: 客户退货处理流程
负责人: 客服部
创建时间: 2025-01-15
```

这和 Excel 表格、Word 表格有什么不同？

| 对比维度 | Excel / Word 表格 | YAML |
|---------|------------------|------|
| **阅读体验** | 需要打开 Excel 才能看 | 直接用记事本打开，文字一目了然 |
| **机器解析** | 需要专门工具读取 | 任何编程语言都能直接读取 |
| **版本管理** | 合并改动容易冲突 | 文字差异清晰，适合 Git 管理 |
| **嵌套表达** | 需要多sheet或合并单元格 | 自然支持多层级结构 |

---

## 为什么要把流程拆成 4 个文件？

一个完整的业务流程，包含的信息是**多层次**的：

```
一个"退货处理流程"
├── 它叫什么名字？谁创建的？（基础信息）
├── 有哪些步骤？每个步骤做什么？（流程步骤）
├── 哪些地方需要判断条件？（决策分支）
└── 有没有时间要求？质量标准？（关键指标）
```

如果把所有信息塞进一个文件，这个文件会变得又长又乱，查一个问题要翻半天。

所以，系统把流程拆成 **4 个独立文件**，每个文件专注一类信息，职责清晰、互不干扰。

---

## 四个文件各自装的是什么？

### 1. basic_info.yaml — 流程的基础档案

相当于一个"名片"，记录这个流程的基本信息。

**示例内容：**

```yaml
流程名称: 客户退货处理流程
版本号: 1.2
创建时间: 2025-01-15 14:30:00
创建人: 张三
所属部门: 电商运营部
流程描述: >
  描述：当客户提交退货申请后，
  客服在4小时内完成审核，
  仓库在24小时内完成收货确认，
  财务在1个工作日内完成退款。
适用场景:
  - 电商平台 B2C 退货处理
  - 客户因个人原因或质量问题申请退货
版本更新记录:
  - 时间: 2025-01-16
    更新人: 李四
    变更内容: 补充了质量问题判断逻辑
```

**这个文件有什么用？**
- 一眼看出这个流程是做什么的、谁负责
- 当有多个人协作时，知道找谁、流程是什么版本
- 想知道"这个流程什么时候建的"，看创建时间就知道了

---

### 2. process_steps.yaml — 流程的"步骤清单"

这是最核心的文件，记录流程中**每一个步骤**的执行内容。

**示例内容：**

```yaml
流程步骤:
  - 步骤编号: step_001
    步骤名称: 客户提交退货申请
    执行动作: >
      客户登录平台，填写退货申请表单，
      包括：退货原因、期望处理方式（退款/换货）、
      上传凭证（照片/视频）
    责任角色: 客户
    输入项:
      - 退货申请表单
      - 凭证材料
    输出项:
      - 退货申请单（系统生成）
    完成条件: 客户提交并确认

  - 步骤编号: step_002
    步骤名称: 客服审核退货申请
    执行动作: >
      客服登录工单系统，查收退货申请，
      核实：订单信息、退货原因、凭证真实性，
      做出审核结论（通过/驳回）
    责任角色: 客服
    输入项:
      - 退货申请单
      - 订单详情
    输出项:
      - 审核结论（通过/驳回）
      - 退货单号
    完成条件: 客服提交审核结论
    时间要求: 接到申请后4小时内完成

  - 步骤编号: step_003
    步骤名称: 仓库收货确认
    执行动作: >
      仓库收到退货商品后，
      清点数量、检查商品状态（是否影响二次销售），
      在系统中确认收货
    责任角色: 仓库管理员
    输入项:
      - 实物商品
      - 退货单号
    输出项:
      - 收货确认单
      - 商品状态报告（完好/损坏）
    完成条件: 仓库在系统中确认收货
    时间要求: 收到商品后24小时内确认
```

**这个文件有什么用？**
- 任何一个新员工，看完这个清单就知道"我需要做什么"
- 招聘新员工时，直接把这个文件给他，比口头交代清楚得多
- 检查流程时，看看有没有步骤遗漏、责任人不明确的地方

### 3. decision_points.yaml — 流程的"岔路口"

记录流程中所有**需要判断的地方**，即"如果…那么…"的逻辑。

**示例内容：**

```yaml
决策分支:
  - 决策编号: decision_001
    决策名称: 退货原因判定
    决策描述: 根据客户提交的退货原因，判断处理方式
    判断条件: 退货原因 = "质量问题"
    为真时: 转向【运费责任方: 商家承担】
    为假时: 转向【运费责任方: 客户承担】
    依据来源: 客户提交的退货申请表单 + 凭证材料

  - 决策编号: decision_002
    决策名称: 商品状态判定
    决策描述: 仓库收到退货后，检查商品是否可以二次销售
    判断条件: 商品状态 = "完好（不影响二次销售）"
    为真时: 转向【退款：全额退款】
    为假时: 转向【退款：扣除折旧费 + 运费】
    依据来源: 仓库验收员的实物检查

  - 决策编号: decision_003
    决策名称: 审核结论判定
    决策描述: 客服审核客户提交的退货申请
    判断条件: 审核结论 = "通过"
    为真时: 转向【生成退货单，等待客户寄回商品】
    为假时: 转向【通知客户审核驳回，流程结束】
    依据来源: 客服的人工判断 + 平台规则
```

**这个文件有什么用？**
- 清晰呈现"哪些地方容易出问题"——这些就是流程中的**关键控制点**
- 当纠纷发生时，可以回溯："当初判断的依据是什么？标准是什么？"
- 客服培训时，重点教这些判断点的处理方法

### 4. key_metrics.yaml — 流程的"健康指标"

记录流程中所有**可量化的时间要求和质量标准**。

**示例内容：**

```yaml
时间要求:
  - 指标编号: time_001
    指标名称: 客服审核时效
    指标描述: 从客户提交退货申请到客服完成审核的最长时间
    要求值: 4小时
    测量起点: 客户提交退货申请的时间戳
    测量终点: 客服提交审核结论的时间戳
    超时处理: >
      系统自动发送催办通知给客服主管，
      24小时未审核则升级至店长处理

  - 指标编号: time_002
    指标名称: 仓库收货确认时效
    指标描述: 从商家收到退货商品到仓库确认收货的最长时间
    要求值: 24小时
    测量起点: 物流显示"商品签收"的时间戳
    测量终点: 仓库管理员在系统中确认的时间戳
    超时处理: >
      系统自动提醒仓库主管，
      48小时未确认则自动标记"异常"并通知客服

质量标准:
  - 指标编号: quality_001
    指标名称: 审核准确率
    指标描述: 客服审核结论经事后复核，确认正确的比例
    要求值: "≥ 98%"
    统计周期: 每月
    数据来源: 质检专员抽样复核记录
    用途: 客服绩效考核参考指标之一

  - 指标编号: quality_002
    指标名称: 退货原因误判率
    指标描述: 因客服判断错误（将非质量问题判定为质量问题）导致的退款纠纷比例
    要求值: "≤ 1%"
    统计周期: 每季度
    数据来源: 客服投诉记录 + 退款纠纷台账
    用途: 识别培训需求，改进审核标准

风险提示:
  - 风险描述: 促销高峰期（双11、618）退货申请量可能激增3-5倍
    影响范围: 客服审核时效、仓库收货确认时效
    建议预案: >
      提前备货、增加临时客服和仓库人手，
      峰值期间临时将审核时效要求放宽至8小时
```

**这个文件有什么用？**
- 把"不能超过几天""必须达到什么标准"写清楚，考核有据可依
- 当出现超时或质量不达标时，可以追溯是哪一步出了问题
- 年度总结时，统计数据是否达标，作为流程优化决策的依据

## 四个文件的关系图

```
basic_info.yaml
│   流程名片：名称、版本、谁负责
│
└── process_steps.yaml
    │   步骤清单：谁、做哪几步
    │
    ├── decision_points.yaml
    │   岔路口：如果…那么…的判断逻辑
    │
    └── key_metrics.yaml
        时间要求：每步不能超过多久
        质量标准：必须达到什么水平
        风险提示：哪些时候容易出问题
```

## 一句话总结每个文件

| 文件 | 一句话总结 |
|------|-----------|
| basic_info.yaml | "这个流程叫什么，什么时候建的，谁负责" |
| process_steps.yaml | "从头到尾有哪些步骤，谁做什么" |
| decision_points.yaml | "哪些地方要判断，判断的标准是什么" |
| key_metrics.yaml | "每一步的时间要求和质量标准是什么" |

## 常见问题

**Q：我不技术，能看懂 YAML 文件吗？**
> A：完全可以。YAML 的设计就是让非技术人员也能读懂。只要你知道"缩进表示层级、减号表示列表项"这两条规则，就能看懂内容。

**Q：导出了 YAML 之后在哪里用？**
> A：YAML 文件可以被各类系统导入和解析，常见用途包括：导入到流程引擎自动执行、导入到低代码平台生成审批流程、导入到培训系统生成 SOP 文档等。

**Q：4 个文件我可以只导出其中几个吗？**
> A：可以。在导出选项中，你可以选择只导出需要的文件类型。
