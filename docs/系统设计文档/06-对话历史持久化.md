# 06 · 对话历史持久化

> 核心实现：
> - 后端：`backend/app/routers/query.py` — 对话历史文件读写 + `is_complete` 判断
> - 前端：`frontend/src/components/tabs/DialogueTab.tsx` — 挂载时加载 + 分支渲染逻辑

## 一、问题背景

对话式梳理是一个**多轮交互**过程，用户在一个 Tab 里多轮对话，Tab 切换后对话历史必须保留。如果历史存在 React 组件 state 里，组件卸载（切换 Tab）后 state 丢失。

**解决思路**：后端将对话历史写入文件，前端每次挂载时从后端加载。

## 二、持久化文件

```
processes/{processId}/
├── dialogue_history.json    ← 对话历史文件（核心）
├── knowledge.json            ← 完成后写入的结构化数据
└── processes/
    ├── main.yaml
    └── ...
```

### dialogue_history.json 结构

```json
{
  "history": [
    { "role": "user", "content": "我想做一个请假流程" },
    { "role": "assistant", "content": "好的，请问你希望这个流程由谁触发？" },
    { "role": "user", "content": "员工发起，主管审批" },
    { "role": "assistant", "content": "明白了。请假原因需要填写吗？" }
  ],
  "is_complete": false
}
```

- `"history"`：每轮 user + assistant 消息对
- `"is_complete"`：`false` = 仍在对话中，`true` = 收集完毕已转为知识结构

## 三、后端实现

### 3.1 加载历史（GET /api/query/dialogue/{processId}/history）

```python
@router.get("/dialogue/{processId}/history")
def get_dialogue_history(processId: str):
    history_file = pdir / "dialogue_history.json"
    if not history_file.exists():
        return {"history": [], "is_complete": False}

    with open(history_file, "r", encoding="utf-8") as f:
        data = json.load(f)
    return {
        "history": data.get("history", []),
        "is_complete": data.get("is_complete", False),
    }
```

**特点**：
- 文件不存在时返回空历史（而非报错）
- 直接读取 JSON 文件，无内存状态依赖

### 3.2 保存历史（POST /api/query/dialogue）

每次对话后，根据是否完成，分两种写入策略：

**非完成状态（is_complete=false）**：
```python
# 追加 user + assistant 两条消息到历史
chat_history.append({"role": "user", "content": body.message})
chat_history.append({"role": "assistant", "content": raw_reply})
with open(history_file, "w", encoding="utf-8") as f:
    json.dump({"history": chat_history, "is_complete": False}, f, ...)
```

**完成状态（is_complete=true）**：
```python
# 生成 YAML 文件
output_dir = pdir / "processes"
output_dir.mkdir(parents=True, exist_ok=True)
_write_yaml(output_dir / "main.yaml", extracted_data["main"])
_write_yaml(output_dir / "decision-tree.yaml", extracted_data["decision_tree"])
_write_yaml(output_dir / "exceptions.yaml", extracted_data["exceptions"])

# 写 knowledge.json（前端知识Tab展示用）
with open(pdir / "knowledge.json", "w", encoding="utf-8") as f:
    json.dump({
        "is_complete": True,
        "extracted_data": extracted_data,
        "updated_at": datetime.now().isoformat(),
    }, f, ensure_ascii=False, indent=2)

# 清理对话历史（重新开始）
if history_file.exists():
    history_file.unlink()
```

**为什么完成后要删历史文件？**
- 对话完成后，`is_complete=true`，历史任务已完成
- 如果保留历史，下次加载时会有残留消息影响新的对话
- `knowledge.json` 已经保存了对话产出的结构化数据，不需要历史文件

## 四、前端实现

### 4.1 挂载时加载历史

```typescript
useEffect(() => {
  if (mode !== "dialogue") return;
  api_dialogue.getHistory(processId)
    .then(({ history, is_complete }) => {
      if (history.length > 0) {
        setHistory(history);  // 恢复历史到 state
      }
      if (is_complete) {
        setHistory([]);       // 已完成则清空（无需恢复）
      }
    })
    .catch(() => { /* ignore */ });
}, [processId, mode]);
```

### 4.2 渲染逻辑：reply 与 history 的互斥

这是踩过一个 bug 之后的关键设计：**对话渲染只能从单一数据源获取**，不能 `reply` state 和 `history` state 同时渲染同一条消息。

```typescript
async function handleSend() {
  const userMsg = input.trim();
  setInput("");
  setDialogueLoading(true);
  setReply("");  // 先清空 reply state

  // 乐观更新：先把用户消息加入 history
  const newHistory: DialogueTurn[] = [...history, { role: "user", content: userMsg }];
  setHistory(newHistory);

  try {
    const res = await api_query.dialogue(processId, userMsg, newHistory);

    if (!res.is_complete) {
      // 非完成：assistant 回复通过 history 渲染
      setHistory([...newHistory, { role: "assistant", content: res.reply }]);
      setReply("");  // 清空 reply，防止重复
    } else {
      // 完成：reply 用于最终一次渲染（立即展示 "收集完毕"）
      setReply(res.reply);
    }
  } catch (err) {
    setHistory([...newHistory, { role: "assistant", content: errMsg }]);
  } finally {
    setDialogueLoading(false);
  }
}
```

**互斥规则**：
- `is_complete=false`（对话中）→ 只通过 `history` 渲染，`reply` 必须清空
- `is_complete=true`（已收集完毕）→ `history` 清空（已完成），通过 `reply` 渲染最终结果

### 4.3 is_complete 的检测机制

后端在 LLM 回复中用正则检测 `is_complete` 标记：

```python
import json, re

json_match = re.search(r"```json\s*(\{.*?\})\s*```", raw_reply, re.DOTALL)
if json_match:
    parsed = json.loads(json_match.group(1))
    is_complete = parsed.get("is_complete", False)
    extracted_data = parsed.get("extracted_data")
```

LLM 被引导在回复末尾输出：
```
我已经收集到足够信息，正在生成结构化文档...

```json
{"is_complete": true, "extracted_data": {...}}
```
```

## 五、has_knowledge 判断逻辑

KnowledgeTab 是否展示，取决于 `has_knowledge`（定义在 processes.py）：

```python
def has_knowledge(process_id: str) -> bool:
    pdir = BASE_DATA_DIR / process_id
    processes_dir = pdir / "processes"
    if not processes_dir.exists():
        return False
    return any(processes_dir.glob("*.yaml"))
```

**为什么加了 `knowledge.json` 检查后又要改回？**

原设计中只有 YAML 文件存在时才展示知识结构。但对话式梳理完成后，`knowledge.json` 里才有数据，而 `processes/` 目录里可能还没有 YAML 文件。

后改为直接写 `processes/main.yaml` 等文件，所以 `has_knowledge` 只需要检查 `processes/*.yaml` 即可——这是文档抽取和对话梳理共用同一套文件结构带来的好处。

## 七、bug 修复记录

### 问题：同一个回答展示两次

**根因分析**：
1. `setReply(res.reply)` 在 if/else 判断之前无条件执行 → assistant 消息在 reply state 中
2. if/else 两个分支里都调用了 `setHistory([...newHistory, ...])` → history 里也有一份

**结果**：同一条消息既出现在 `reply` state（实时渲染），又出现在 `history` state（历史渲染），DOM 里渲染两次。

**修复**：
- 将 `setReply(res.reply)` 只保留在 `is_complete=true` 分支
- 在 `is_complete=false` 分支中显式 `setReply("")` 清除 reply state
- history 追加只发生在 `is_complete=false` 分支

```typescript
// 修复后
if (!res.is_complete) {
  setHistory([...newHistory, { role: "assistant", content: res.reply }]);
  setReply("");  // ← 关键：防止 reply 和 history 同时渲染同一条
} else {
  setReply(res.reply);
}
```
